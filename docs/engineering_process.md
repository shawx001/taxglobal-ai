# TaxGlobal AI 工程执行流程标准（PLM）

日期：2026-06-02
状态：生效（v1.0）
适用范围：TaxGlobal AI 全部研发工作（含每个 Step N 功能交付）

---

## 0. 为什么要这份文档

把一个项目从"想法"到"下线"用一套可重复的流程管起来，避免：盲目开工、没评审就写代码、没测试就上线、出了事故没人复盘。

本文件分两部分：
1. **完整标准**：互联网大厂（阿里/腾讯/字节式）标准的 6 阶段项目生命周期（PLM）。这是"满配"形态。
2. **本项目适配**：TaxGlobal AI 当前是单人 + AI 协作 + 未上线 MVP。满配 PLM 直接照搬就是过度设计（违反我们自己的工程底线）。所以每个环节标注 **保留 / 简化 / 暂缓**，并给出"每个功能步骤的最小卡点"。

---

## 1. 完整标准：6 阶段生命周期

```
[1.需求与启动] → [2.设计与评审] → [3.研发与测试] → [4.发布与上线] → [5.运维与度量] → [6.复盘与演进]
     Define          Design            Develop           Deploy           Monitor           Review
```

### 阶段 1：需求与启动（Define）—— 做什么、为什么做
- **BRD/MRD**：业务/市场需求文档，论证商业价值与 ROI。
- **PRD 三方评审**：PM 输出 PRD，组织 PM / 研发 / QA 三方评审。
- **Kick-off 启动会**：明确排期（Milestones）、接口人、关键里程碑（50% 进度、联调、提测、上线时间）。

### 阶段 2：设计与评审（Design）—— 怎么做（决定底层质量）
- **技术方案设计（Design Doc）**：架构图（分层/依赖/数据流）、技术选型（含为什么）、数据库设计（ER 图/表结构/索引/分库分表）、接口设计（API/状态码/上下游依赖）、非功能性设计（降级/限流/安全/资损防控）。
- **技术评审（Tech Review）**：架构师 + 资深开发 + 安全专家挑战方案漏洞，通过才定稿。
- **测试用例评审（Test Case Review）**：QA 依据 PRD + 技术方案写用例，研发共同评审，确保理解一致。

### 阶段 3：研发与测试（Develop）—— 代码落地 + 质量把控
- **分支管理**：Git Flow，从 `master` 拉 `feature/*` 独立开发。
- **自动化卡点**：Lint（IDE / Git Hooks 强制）、单元测试（核心业务覆盖率 ≥ 80%）。
- **Code Review**：合入公共分支前必须发 PR，1–2 名资深工程师逐行审查。
- **冒烟测试**：研发自测 + 过核心冒烟用例后才提测（Lock Code）。
- **多轮集成测试**：功能测试（FAT）、性能测试（PT：QPS/RT/CPU/内存）、安全合规扫描（CVE/越权）。

### 阶段 4：发布与上线（Deploy）—— 不影响线上用户
- **预发验证（Staging）**：1:1 复制生产，连真实只读库/影子库，做 Staging 拔测。
- **变更评审与上线审批**：上线清单（配置项、SQL 执行顺序、回滚方案），组长/运维审批。
- **灰度发布**：蓝绿/金丝雀（先 1% 流量看错误日志）→ 分批 10%→50%→100%；功能开关（Feature Toggle）动态控制。

### 阶段 5：运维与度量（Monitor）—— 长期健康
- **立体化监控告警**：基础（CPU/内存/磁盘/IO）、应用 APM（QPS/RT/错误率/链路追踪）、业务（订单量/支付成功率等核心指标）。
- **日志收敛**：ELK/SLS 全量日志，ERROR 级即时告警（钉钉/企微/邮件）。

### 阶段 6：复盘与演进（Review）—— 团队成长 + 系统优化
- **项目复盘（Post-Mortem）**：度量（排期偏差、千行代码缺陷率、线上故障数）、经验沉淀。
- **故障复盘（若有）**：故障定级、5 Whys 根因分析、产出可落地 Action Items（责任到人）。

## 2. 本项目适配（单人 + AI 协作 + 未上线 MVP）

原则：**保留所有"防止给用户假确定性 / 防止数据不可追溯 / 防止改坏已验证逻辑"的卡点；简化纯多团队协作开销；暂缓需要真实流量/生产环境的环节。**

| 阶段 | 环节 | 决策 | 在本项目怎么做 |
|---|---|---|---|
| 1 Define | BRD/MRD | 简化 | 已有 PRD v1.1 + 项目计划书 v3.1，补一份轻量 Charter（见 `docs/phase1_define_us_mvp.md`） |
| 1 Define | PRD 三方评审 | 保留(角色合并) | Shaw 戴 PM/研发帽，Claude 充当独立 QA/评审，记录评审意见 |
| 1 Define | Kick-off | 保留 | 里程碑 = 现有 Step 0–11；每步开工前写"本步目标/验收/风险" |
| 2 Design | Design Doc | **保留(关键)** | 每个 Step 写一份精简 Design Doc：数据契约、函数签名、拒绝路径、非功能点 |
| 2 Design | Tech Review | 保留(由 Claude 担任) | 提交前让 Claude 挑战方案；安全/合规视角必须覆盖（税务=资损/合规敏感） |
| 2 Design | 测试用例评审 | **保留(关键)** | 写实现前先列测试用例（含拒绝/边界/黄金值），Claude review 用例完整性 |
| 3 Develop | 分支管理 | 简化 | 单人可直接在 `main` 小步提交；**建议**改为 `feature/stepN` + PR，留 CR 痕迹 |
| 3 Develop | Lint | **待补(缺口)** | 目前无 Lint。建议引入 `ruff`（Python）+ pre-commit hook |
| 3 Develop | 单测覆盖率 | **保留** | 核心税务/拒绝路径必须有测试；Step 3 黄金测试集是专门一步 |
| 3 Develop | Code Review | 保留(由 Claude 担任) | 每个 commit 由 Claude 逐项 review + 独立验证（已在做） |
| 3 Develop | 冒烟/FAT | 保留 | 验证脚本 + unittest 充当；前端接通后加端到端冒烟 |
| 3 Develop | 性能测试 | 暂缓 | 无并发场景；FastAPI 上线前再压测核心 `/calc/*` |
| 3 Develop | 安全/CVE 扫描 | **待补** | 引入 `pip-audit`/依赖扫描；现无第三方重依赖，成本低 |
| 4 Deploy | Staging / 灰度 / 回滚 | 暂缓 | 未上线。保留"可回滚"原则（小步 commit + 旧规则 superseded 不删） |
| 4 Deploy | Feature Toggle | 暂缓 | 待多用户/线上后引入 |
| 5 Monitor | APM / 日志告警 | 预留接口 | 工程底线已要求"可观测性从早期预留"；engine/API 记录耗时与错误结构 |
| 6 Review | 项目复盘 | 保留(轻量) | 每个 Step 的"已知限制"+ 阶段性回顾即为复盘 |
| 6 Review | 故障复盘 5 Whys | 保留(触发式) | 一旦出现"算错税/给了无来源结论"，强制 5 Whys + Action Items |

**当前最大的标准缺口（按优先级）**：①无 Lint/格式化卡点；②无依赖安全扫描；③单人直推 `main`、无 PR/CR 留痕；④无 CI（上述卡点未自动化）。这些是进入"多功能并行 + FastAPI"前最该补的工程基建。

## 3. 每个功能步骤（Step N）的最小执行卡点

每个 Step 必须依次过完以下卡点，缺一不可（对应大厂 6 阶段的精简版）：

```
[Define] 写清本步目标 / 验收标准 / 已知风险
   ↓
[Design] 精简 Design Doc：数据契约 + 函数签名 + 拒绝/边界路径 + 非功能点(安全/可追溯/可回滚)
   ↓
[Test-First] 先列测试用例（成功 + 拒绝 + 边界 + 黄金值），Claude review 用例
   ↓
[Develop] 小步实现；Lint 通过；不裸写税务数字；不静默降级
   ↓
[Review] 发起变更集；Claude 逐项 CR + 独立验证（重算/跑测试/负向测试）
   ↓
[Verify] 单测 + 数据校验 + hash/diff 检查全绿；commit message 写 目的/验收/风险
   ↓
[Retro] 在 docs/stepN_*.md 记录 已做/验收结果/已知限制（即轻量复盘）
```

## 5. 角色（一人多帽 + AI）

- **Shaw**：PM（定需求/优先级）+ Tech Lead（定方案）+ Developer（实现）。
- **Claude**：独立 QA + Code Reviewer + Tech Reviewer（安全/合规视角）。职责是**挑战、独立验证、不放水**，而非替 Shaw 拍板业务决策。
- 上线后如引入更多人：把"评审"从"Claude 单点"扩为"人 + Claude"双签。
