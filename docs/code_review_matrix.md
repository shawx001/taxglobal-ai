# 多智能体代码审查矩阵（Multi-Agent Review Matrix）

> 适用：**每个 PR** 的深度会审。与 `code_review_checklist.md`（5 维大厂 CR）+ 本项目 #1 原则（**数值精确到分 + 官方源可溯**）**叠加**，不取代。
> 抗压边界：审查时**必须先读 `/ARCHITECTURE.md`**，按"当前真实架构"评估，**严禁为尚不存在的组件臆造风险**（见 §0）。
> 输出纪律：**严禁命名/缩进/格式等无用 Nitpick**；只报**中/高/致命级**隐患。

## 0. 抗压边界与去幻觉（最重要）
审查前先读 `/ARCHITECTURE.md`（峰值 QPS、技术栈、外部强依赖）。当前系统是**无状态纯函数税务引擎**：FastAPI + 本地版本化 JSON 规则（`@lru_cache`），**无数据库 / 无 Redis / 无外部 API / 无鉴权 / 热路径无磁盘网络 IO**。因此：
- **现在不适用、不得臆造**：SQL 注入、N+1、慢查询、死锁、缓存击穿/穿透/雪崩、连接池打满、越权(IDOR)、鉴权绕过——**这些组件还不存在**。强报即幻觉，违反去噪纪律。
- **现在真正生效的审查焦点**（纯计算引擎）：①**数值正确性到分** + 公式/阈值只来自版本化数据、可溯官方源；②**输入健壮性**（空/负/NaN/超范围 → 422 或 invalid_input，绝不静默算错数）；③纯函数无共享可变状态（横向扩展安全）；④返回结构契约一致；⑤前端空-vs-0、响应判空、后端不可用提示。
- **M2+ 才解锁**（DB / 知识库 GraphRAG / LangChain Agent / 连接器 / 自有模型）：届时下面安全/性能/SRE 各项**全面生效**，按 `ARCHITECTURE.md` 当时的栈评估。

## 1. 审查矩阵：5 个专家 Agent（由 Claude 一人分饰，逐角色过一遍）
**[Security 安全审计]**
- 注入与越权：SQLi / XSS / OS 命令注入；水平/垂直越权(IDOR)；未授权接口。
- 数据与密钥：禁硬编码 Secret/Token/明文密码；敏感数据(手机号/身份证/收入)加密传输与存储合规。
- 依赖漏洞：新引入第三方库的已知严重 CVE（pip-audit）。

**[Performance 性能/高并发]**
- DB 极限：循环查库(N+1)、未命中索引慢查询、大表更新死锁。
- 内存/资源：大对象高频创建的 GC 压力；未关闭 IO/长连接的资源泄露。
- 并发安全：race condition、线程不安全结构、锁粒度过粗致吞吐骤降。

**[SRE / 高可用]**
- 雪崩/过载：突发 10x 流量是否拖垮下游？核心链路是否有超时(Timeout)、重试风暴控制、降级/熔断？
- 缓存一致性：击穿/穿透/雪崩；大并发下缓存与 DB 不一致的极端边界。
- 可观测性：关键分支是否有 metrics 埋点 + Error 级日志，出事能 1 分钟内定位？

**[Domain Architect 领域架构]**（本项目权重最高之一）
- **税务数值正确性**：到分、跨收入交叉（共享 SS 基数 / 合并 Additional Medicare / QBI 阈值与 phase-in / QDCGT 叠加 / NIIT / FEIE 叠加）；规则=数据、不裸写；可溯 Rev.Proc./DOR。
- 架构一致性：联邦-州拆分、引擎门面后的小模块、数据驱动（新州/年=只改数据）；防过度/不足工程。

**[Tax Compliance Specialist 税务专家]**（本项目权重最高之一；不只验"代码对",更验"税法对/专业"）
- **对照官方 worksheet/法条**(IRS Form 1040 instructions、Foreign Earned Income Tax Worksheet、QDCGT/Schedule D Tax Worksheet、Schedule SE、Form 8959/8960/2555、各州 DOR 手册)逐项验**税务处理是否专业正确**,而非只看代码逻辑自洽。
- 重点抓**口径自相矛盾 / 跨规则交叉**:如 FEIE 排除收入是否对**普通税与资本利得都垫底**(2026-06 真实抓到:只垫了普通税,LTCG 少算);QBI 整体限额是否排净资本利得;NIIT 的 MAGI 是否加回 FEIE;SE 税半额扣除;申报身份阈值。
- **独立第二推导**:不复用 Claude 自己的参考实现(它可能与引擎共享同一建模错),从官方 worksheet 重新推导关键数,逐分对。命中即给"错值 vs 正确值 + 法条出处"。

**[Lead Coordinator 主协调]**
- 去噪、去幻觉、去重；按 `ARCHITECTURE.md` 校准风险真实性；汇总**仅中高级+**的高价值报告;对事不对人。

## 1.1 运行节奏（节流 token）
- **每个大 block 完成后跑一次完整多 agent 会审**(并行真 subagent,含上面税务专家),作为该 block 的"出厂质检"。
- **平时小任务/小 PR 单条 review 即可**(Claude 单脑过矩阵实质 + 逐分核 + 按 ARCHITECTURE 边界裁剪)——不为小改动消耗多 agent。
- **但写码时必须自带工业级 sense、一次写对**:防御性输入/数值到分/数据驱动/无状态——**不指望后续 review 纠错**(review 是安全网,不是主纠错手段)。

## 2. 输出格式（只报中/高/致命）
```
### 🚨 [风险级别: 致命/高危/中危] 隐患简述 (归属 Agent 标签)
* 具体位置：`文件名:行号`
* 根源分析：大并发/攻击场景下为什么会崩 / 算错？
* 抗压/修复方案：符合最佳实践的重构代码片段。
```
（本项目数值类隐患额外要求：给出**到分的错值 vs 正确值**与触发输入。）

## 3. 对抗演练 Agent（专职，按需追问）
除静态会审外，对**有外部接口/状态/依赖**的改动追加对抗演练（当前纯计算引擎多为 N/A，M2+ 必做）：
- **追问1 压测模拟（@Performance）**：「生产峰值 QPS=<见 ARCHITECTURE.md>，用户同时打这次改动的接口，推演内存/CPU 热点函数在哪？数据库连接池会否瞬间占满？」
- **追问2 防御破坏（@Security 扮黑客）**：「针对新接口，有哪些手段绕过鉴权 / 构造畸形参数把服务打满(DoS)？给出攻击路径。」
- **追问3 监控埋点补全（@SRE）**：「若上线后假死，用 Prometheus/Grafana 该监控哪个关键指标最快报警？当前日志够排查吗？不够则补全埋点/日志。」
> 当前引擎：压测=纯 CPU、无连接池（无 DB）；DoS 面=输入校验/请求体大小（已 422/invalid_input）；可观测性=已有 request_id + 结构化日志。M2+ 接 DB/KB/Agent 后这三问全面展开。

## 4. Claude 如何执行
每个 PR review：先读 `ARCHITECTURE.md` → 逐角色过 §1 矩阵（按 §0 边界裁剪适用项）→ 本项目**必做**:逐行 review + **逐分独立重算**(自建参考,不只对引擎自身)+ 官方源交叉核 + 防御性输入 + golden 回归 → 按 §2 只报中高级+ → Coordinator 去噪汇总。发现的真实隐患写进对应文档/记忆。
