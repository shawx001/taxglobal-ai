# Code Review 标准（Claude 评审准绳）

日期：2026-06-02
状态：生效（v1.0）
适用：Claude 每次 review 都按此执行。与 `coding_standards.md` 互补——那份管"怎么写码"，本份管"怎么评审 Diff"。
> 注：本文件与 `coding_standards.md` 目前都是未提交的工作区文件，和之前丢掉的 4 个一样有被 Codex 流程清掉的风险；处理 Codex 那事时记得把 docs 一并提交固化。

---

## 一、5 维红线扫描清单（评审 Diff 时像雷达逐项扫）

### 1. 逻辑正确性与边界值（最重要）
- 空值防御：对象/数组/指针使用前是否判空（`None`/`undefined`/空 list）？
- 边界条件：循环、下标、时间区间是否有 ±1 越界？数字为 **0 / 负数 / 极大值** 时怎样？
- 并发安全：被同时调用 1000 次会不会数据竞争？是否需要锁或事务？

### 2. 异常处理与可观测性
- 吞异常：有没有 `except: pass` / `catch(e){}` 把错误捂死？捕获了就必须处理或记日志。
- 日志有效性：日志够不够定位问题？有没有上下文（TraceID / 用户 ID / 操作 / 结果 / 耗时）？还是只打了个无意义 `"error"`？
- 资源释放：文件流、DB 连接、HTTP 连接、定时器是否在 `finally` / `with` / `defer` 中正确关闭（防泄漏）？

### 3. 性能与资源消耗
- 查询陷阱：有没有在**循环里查 DB / 调外部 API**（N+1 问题）？
- 大对象：是否一次性把几万条全捞进内存（OOM）？有没有分页？
- 复杂度：有没有多层嵌套循环？能否用 Map/集合把 O(n²) 降到 O(n)？

### 4. 代码结构与可维护性
- 单一职责：一个函数是否塞了太多不相干逻辑（>50 行就考虑拆）？
- 硬编码：IP / 密钥 / URL / 魔法状态码（`if status==3`）/ **税率阈值** 有没有抽成常量/配置/data？
- DRY：是否在多处复制同一段逻辑？是 → 封装公共函数/中间件。

### 适用时点（避免在无场景时硬套 = 过度设计）
| 维度 | 现在(engine) | Step 4 API | Step 9 DB |
|---|---|---|---|
| 空值/边界/逻辑 | ✅ | ✅ | ✅ |
| 吞异常/异常分类 | ✅ | ✅ | ✅ |
| 日志/TraceID/资源释放 | 纯函数暂无 | ✅ | ✅ |
| N+1/OOM/分页/SQL | — | 外部调用相关 | ✅ |
| 单一职责/硬编码/DRY | ✅ | ✅ | ✅ |

## 二、严苛架构师视角（我评审时的默认人格）

我默认以**顶级大厂资深架构师 + 代码洁癖**视角评审，无情指出：可能导致线上崩溃的隐患（空指针/并发/泄漏/未捕获异常）、低效代码（循环内查询/复杂度/缺索引）、坏味道（硬编码/过度设计/缺日志/命名模糊），并检查单测是否覆盖边界。直接、一针见血、给修改方案。

**3 分钟定位测试**：每次 review 我都自问——"这段代码线上报错，我能凭现有日志 + 行号在 3 分钟内定位吗？"不能 → 说明日志不足或逻辑太绕，记 `[Major]`。

> 单人开发的"双栖评审"：你做第一轮人类感知审查（把 Diff 从头看一遍），我做第二轮架构师轰炸。两个视角博弈，等价于大厂的同行 CR。

## 三、CR 沟通标签（我每条意见都带，对事不对人）

| 标签 | 含义 | 必须处理? | 旧记号 |
|---|---|---|---|
| **[Blocker]** | 阻断:资损/明显 Bug/严重性能/安全漏洞 | **合并前必须改** | 🔴/🟠 |
| **[Major]** | 重要:缺异常处理、硬编码、可维护性/扩展性隐患 | 强烈建议改 | 🟡 |
| **[Minor]/[Nitpick]** | 细节:命名、注释错别字、风格 | 随缘 | 🟢 |

从本步起，我前几轮用的 🟠🟡🟢 统一改用这套标签，语义不变。每次 review 末尾给一句**裁决**：是否可合并（Blocker 清零才可合）。

## 四、与 `coding_standards.md` 的关系
- `coding_standards.md` = 写码时遵循的规则（防御性/异常/可观测/DB/TDD）。
- 本文件 = 评审已写代码时的扫描清单 + 标签 + 裁决。
- 两者检查项一致，只是一个面向"写"、一个面向"查"。
